# JIT Plan B 执行路线

这份文档说明 JIT 项目现在走到哪里、为什么可以停止继续训练 Phase U，
以及接下来怎样从现有策略出发，完成 Phase D、状态评分网络和最终统一策略。

这是一份总路线。后面真正开始某一阶段时，还需要为那一阶段单独写配置、测试和
运行记录，不能把后面还没有实现的内容说成已经完成。

## 1. 先说结论

当前最新策略可以当作我们的 `pi_up` 候选。

原因很简单：`pi_up` 需要完成的是从地面开始，加速、起跳、上升，并把系统带到
Apex 附近。当前策略已经把这段做完了。它在 Apex 后还会继续给动作，甚至能继续
向前运动很长一段距离，这不影响它作为 `pi_up` 使用。

最新结果来自：

```text
JIT/runs/phase_u/phase_u_v4_pitch15penalty_9977856_seed820901_20260826
```

这次训练完成了 9,977,856 个训练 transitions，checkpoint 可以正常恢复，严格的
run 校验通过。最终自然起点评估是 8/8 到达 Apex，之后才在更晚的时候因为
`pitch_limit` 结束。

因此，按照 Plan B：

- Phase U 的训练任务到这里先结束，不再继续追加训练步数；
- 9,977,856 checkpoint 先作为主要 `pi_up` 候选；
- 4,988,928 和 7,987,200 checkpoint 一起保留，它们能提供不同的 Apex 状态；
- 接下来把主要精力放在 Phase D，也就是下降、落地和短时间恢复；
- 最后不是部署两个策略，而是再训练一个统一策略 `pi_unified`。

这里说“Phase U 完成”，意思是它已经足够支持下一阶段，不是说它已经完美，也不
是说现在已经完成了整个 JIT 方法。

## 2. 为什么现有策略会跳了，还要做 Phase D

我们把训练分成两个阶段，不是因为最后一定要在两个策略之间切换。

两个阶段真正的作用，是把一个很长、很难学的任务拆成两个比较清楚的问题：

1. `pi_up` 负责回答：“怎样从地面到达一个可以继续处理的 Apex 状态？”
2. `pi_down` 负责回答：“从这个 Apex 或下降状态开始，怎样落地并避免马上摔倒？”

现有策略虽然已经完成了整个跳跃动作，但它在下降和落地后的处理不够好。继续用
完整任务反复训练它，可能会破坏已经学会的起跳。Plan B 选择保留已经会跳的部分，
只训练一个专门处理后半段的 `pi_down`。

两个阶段还会给我们两类训练数据：

- 上升过程中的状态，用来学习 `V_up`；
- Apex、下降和落地过程中的状态，用来学习 `V_down`。

可以把 `V_up` 和 `V_down` 理解成两张“状态地图”：

- `V_up` 给一个状态打分，表示从这里继续使用 `pi_up`，到达 Apex 的希望有多大；
- `V_down` 给一个状态打分，表示从这里继续使用 `pi_down`，完成落地恢复的希望有
  多大。

之后我们根据这两张地图，挑选适合训练的状态区域，再训练一个统一策略。最终
实际运行时只使用这一个统一策略，不需要在空中切换网络。

整体流程是：

```text
现有跳跃策略 pi_up
        ↓
收集上升、Apex 和早期下降状态
        ↓
训练下降恢复策略 pi_down
        ↓
用冻结的 pi_up / pi_down 给大量状态做继续执行测试
        ↓
训练 V_up 和 V_down 两张状态评分地图
        ↓
从评分较好、同时有一定边界覆盖的区域建立 soft Tube
        ↓
从现有 pi_up 初始化，训练一个最终统一策略 pi_unified
        ↓
独立评估完整跳跃能力
```

## 4. 执行时一直遵守的几条原则

1. 不再从头训练 Phase U，也不继续给当前 Phase U 追加 PPO 步数。
2. 不把 Apex 后的摔倒算成 Phase U 失败，那是 Phase D 要解决的问题。
3. hip 和 knee 的力矩不作为 Phase U 或 Phase D 的晋级条件。它们可以记录下来供
   分析，但不因为力矩数值大就否定一次完整跳跃。
4. 不修改现有 XML 中的物理限幅、碰撞体、障碍物和动作顺序。这里说“忽略力矩
   限制”，是指不把它当作结果筛选门槛，不是修改仿真模型。
5. 训练 `pi_down` 时不能使用还没训练好的 `V_down` 或 soft Tube。先把专家训练好，
   再用它生成数据。
6. 成功、物理失败、超时和无效状态必须分开记录，不能全部混成“失败”。
7. 每次正式运行前都要写清楚目的、输入、最大训练量、停止条件和输出目录。
8. 后续能力只有在代码、测试和真实结果都存在时，才可以标成“已完成”。

## 5. 第一步：固定 Phase U，不再继续训练

### 目的

把已经学会的跳跃保留下来，避免继续优化时破坏现有能力，也为后续状态采集提供
固定的来源。

### 如何完成

1. 把下面三个 checkpoint 都保留：

   ```text
   transition_4988928
   transition_7987200
   transition_9977856
   ```

2. 暂时把 `transition_9977856` 记为主要的 `pi_up_candidate`。
3. 记录每个 checkpoint 的策略 hash、配置 hash、XML hash、observation normalizer
   和动作顺序。
4. 再运行一次严格 run 校验，并确认三个 checkpoint 都能够被加载。
5. 不复制或修改原始 run；新的说明文件只引用原始 checkpoint 路径和 hash。

### 为什么保留三个 checkpoint

三个 checkpoint 到达 Apex 时的状态并不完全一样。4.99M 的转动比较快，7.99M
有一些不同的高度和速度，9.98M 更稳定、更重复。Phase D 如果只从一个很窄的
状态开始训练，后面容易只会处理一种落地情况。

### 产物

- 一份冻结候选记录；
- 三个可以恢复的 `pi_up` checkpoint 路径和 hash；
- 明确写下“Phase U 不再继续训练”。

### 做到什么算完成

- 严格 run 校验通过；
- checkpoint 能够恢复并重新跑出相同类型的 Apex 行为；
- 后续代码不会覆盖或继续训练这些 checkpoint。

## 6. 第二步：建立 Apex 和下降状态库（已完成）

当前已完成 168 条 handoff snapshots，覆盖 24 个 parent trajectories 和
三个 source checkpoints，并按 parent seed 保持 train/eval 隔离。以下内容保留
为采集合同和历史执行说明。

### 目的

给 Phase D 准备真正来自当前策略的起点。Phase D 不应该从我们手工想象的空中
姿态开始，而应该尽量从 `pi_up` 实际到达过的状态开始。

### 如何完成

1. 分别加载 4.99M、7.99M 和 9.98M checkpoint，重新在线运行自然起点轨迹。
2. 在以下位置保存 snapshot：

   - Apex 前 5 到 10 个控制 tick；
   - 最接近 Apex 的状态；
   - Apex 后 5 到 10 个控制 tick；
   - 明确进入下降后的若干状态；
   - 第一次可能接触地面或平台之前的状态。

3. 每个 snapshot 不只保存位置和速度，还要保存：

   - `qpos` 和 `qvel`；
   - 连续三帧真实 observation history；
   - 上一个动作和控制量；
   - jump/Apex 等事件状态；
   - 当前控制 tick；
   - 来源轨迹和 checkpoint；
   - 配置、XML 和策略 hash。

4. 现有评估 NPZ 可以帮助找到时间位置，但不能直接冒充正式 snapshot。缺少历史
   信息时，必须重新在线运行策略采集。
5. 在真实状态附近加入小范围变化，例如轻微改变高度、前向速度、下降速度、pitch
   和 pitch rate。
6. 每个变化后的状态都要检查有限值、关节范围、碰撞穿透和短时间动力学。如果
   状态一恢复就爆炸或穿进地面，就丢弃。
7. 把状态分成几组，例如高/低 Apex、快/慢下降、转动较大/较小、接触较早/较晚，
   不要只按总数量统计。

### 产物

- 一个带完整来源信息的 handoff snapshot bank；
- 一份状态分组统计；
- 一组专门留作评估、训练时不会使用的父轨迹。

### 做到什么算完成

- snapshot 保存后能够恢复；
- 恢复后的下一步与原轨迹基本一致；
- 状态库不只包含同一个 Apex 状态的重复副本；
- 每条状态都能追溯到来源 checkpoint 或合法的小范围变化。

## 7. 第三步：实现 Phase D 训练能力（工程栈已完成）

当前已实现 `descent_recovery` reset pool、统一 observation/history/action
合同、actor-only 初始化、独立终止语义和稳定 reward 代码；critic 与 optimizer
保持 fresh。25,600 smoke 和 42-state fixed panel 已验证，panel 结果为 32
success、10 `roll_limit`、0 timeout，失败只来自 4,988,928 source bank。
新 reward 尚未跑真实 smoke 或正式训练。

### 目的

让一个策略专门学习下降、接触和落地后的短时间恢复，而不要求它重新学习地面
加速和起跳。

### 如何完成

1. 扩展现有稳定入口：

   ```text
   JIT/cli/train_phase_expert.py
   ```

   让它除了 `propulsion_ascent`，还能接受 `descent_recovery`。不要再新建带 v1、
   v2 后缀的训练入口。

2. Phase D 继续使用同一个 XML、同一个控制频率、同一套 observation 和动作顺序。
3. Phase D reset 从第二步得到的 snapshot bank 中抽样，不从地面自然起点开始。
4. 建议用当前 `pi_up` 的 Actor 作为初始参数，因为它已经经历过完整空中过程。
5. Phase D 的 critic 和 optimizer 重新开始。这个过程叫“用 Actor 初始化”，不能
   写成“继续恢复 Phase U 训练”，两者的记录要分开。
6. Phase D 的任务过程按下面顺序记录：

   ```text
   合法空中起点
       → 进入下降
       → 发生有效接触
       → 接触后没有马上翻倒
       → 保持一小段可继续行驶的状态
   ```

7. 初步建议把成功定义为：有效落地后连续 25 个控制 tick，也就是 0.5 秒，没有
   物理失败并且仍可继续向前。更长时间的稳定性留到最终评估，不在最开始设置成
   很严的训练门槛。
8. Phase D 奖励只围绕下降姿态、接触质量、避免立即翻倒、继续向前和短时恢复。
   不按照参考轨迹逐时刻追踪，也不加入 `V_down` 或 Tube 奖励。

### 产物

- `descent_recovery` 配置；
- Phase D reset、奖励、成功和终止逻辑；
- Phase D 的评估报告和视频；
- 对应的单元测试和 GPU 测试。

### 做到什么算完成

- Phase D 环境可以从 snapshot 正确恢复；
- 一次 step、一次 PPO update、checkpoint 保存和恢复都能通过；
- 成功、物理失败和超时能够正确区分；
- 视频在真实结束位置停止，不补重复帧。

## 8. 第四步：先跑 Phase D 新 reward smoke（下一步）

### 目的

先确认代码和训练流程没有问题，不用一次就启动很长的训练。

### 如何完成

1. 使用现有 snapshot bank 和 actor-only Phase U 初始化，运行新的 25,600-transition
   Phase D smoke；这一步尚未启动。
2. 先运行完整 JIT preflight：

   ```bash
   bash JIT/scripts/local_preflight.sh
   ```

3. 预先声明 Phase D smoke 的目的、输入 bank、随机种子、训练上限、停止条件和输出
   目录。
4. smoke 建议只跑一个 PPO block，也就是 25,600 个训练 transitions。
5. smoke 后从没有参与训练的 snapshot 组做固定评估，并重复 42-state panel。
6. 检查 loss、KL、动作分布、状态值、终止原因、snapshot 来源和 checkpoint hash。

### 这一轮不要求什么

smoke 的目标是验证工程流程，所以不要求它一定学会落地，也不根据 hip/knee
力矩决定通过或失败。

### 什么时候立即停止

- 出现 NaN 或 Inf；
- snapshot 恢复错位；
- 状态明显穿透或爆炸；
- checkpoint 无法恢复；
- 配置或 hash 与声明不一致；
- 奖励明显鼓励躺平、提前撞地或拖延到超时。

### 做到什么算完成

- smoke 正常结束；
- PPO 确实完成一次更新；
- checkpoint 可以恢复；
- 固定评估和结果统计能够闭合；
- 严格 run 校验通过。

## 9. 第五步：跑一轮有限的 Phase D pilot

### 目的

判断 Phase D 是否真的能从现有 Apex 状态学会落地和恢复，并找出它能处理和不能
处理的状态范围。

### 如何完成

1. smoke 通过后，再单独批准一轮大约 998,400 transitions 的 pilot。
2. 建议在开始、约 256k、512k 和最终位置保存 checkpoint 和固定评估。
3. 每次评估按状态组分别统计：

   - 是否进入下降；
   - 是否发生有效落地；
   - 是否完成 0.5 秒短时恢复；
   - physical failure；
   - timeout；
   - 接触时的速度和姿态；
   - 落地后的前向距离。

4. 不只看平均 reward。平均 reward 上升但稳定恢复仍然为零时，不能说 Phase D
   已经学会。
5. 如果恢复成功开始出现，而且能覆盖不止一种 handoff 状态，可以继续；如果多个
   checkpoint 都没有改善，就先分析失败轨迹，不直接把训练预算放大到几百万或
   几千万。

### 产物

- 一组 Phase D checkpoints；
- 每个 checkpoint 的分组评估；
- 成功和失败视频；
- 一个候选 `pi_down`。

### 做到什么算完成

- 在没有参加训练的父轨迹上出现可以重复的稳定恢复；
- 不只是一个完全相同的状态偶然成功；
- 失败、超时和成功数量全部能够对上；
- 选出一个冻结的 `pi_down_candidate`。

这里仍然不要求所有状态都成功。我们需要的是一个能产生有用正例和反例、能够
继续做状态评分的下降策略。

## 10. 第六步：确定 `pi_up_star` 和 `pi_down_star`

### 目的

确定后面给状态做标签时，到底以哪个固定策略为准。不同 checkpoint 不能混在
一起当作同一个标签来源。

### 如何完成

1. 从 Phase D checkpoints 中选择稳定恢复表现最好、失败原因最正常的一个，冻结为
   `pi_down_star`。
2. 让同一个 `pi_down_star` 分别接管 4.99M、7.99M 和 9.98M `pi_up` 产生的 handoff
   状态。
3. 比较哪个 `pi_up` 产生的 Apex 分布更容易被 `pi_down_star` 接住，同时又有比较好
   的状态覆盖。
4. 如果 9.98M 最合适，就把它定为 `pi_up_star`；如果 7.99M 更容易恢复，就选
   7.99M。这个选择不需要重训 Phase U。
5. 记录两个最终专家的 policy hash、normalizer、配置和固定评估协议。

### 产物

- 一个冻结的 `pi_up_star`；
- 一个冻结的 `pi_down_star`；
- 一份说明为什么选择它们的对比报告。

### 做到什么算完成

- 两个策略都不再变化；
- 每个后续 label 都能明确指出是由哪个策略产生的；
- 选择依据是实际继续执行结果，不是旧 Gate B 的角度或力矩门槛。

## 11. 第七步：给状态做 continuation labels

### 目的

把“这个状态看起来不错”变成“从这个状态继续运行固定策略，实际结果怎样”。这些
结果才是训练 `V_up` 和 `V_down` 的依据。

### 如何完成

1. 收集从地面推进到 Apex 之间的上升状态，交给冻结的 `pi_up_star` 继续运行。
2. 如果最后到达有效 Apex，就记为上游成功；否则记录具体物理失败或超时。
3. 收集 Apex、下降、接触和落地后的状态，交给冻结的 `pi_down_star` 继续运行。
4. 如果最后完成有效落地和短时恢复，就记为下游成功；否则记录具体失败或超时。
5. 普通状态可以先运行较少分支；接近成功/失败边界、结果不稳定的状态再增加分支。
   不设置所有状态都必须跑 4、8、16、32 次的统一硬规定。
6. 所有状态按父轨迹分开。来自同一条轨迹的相邻状态不能一部分进训练集、一部分
   进测试集，否则评分会显得虚高。
7. 早期 checkpoint 收集的候选状态可以保留，但正式训练前必须用最终冻结策略重新
   做一次标签。

### 产物

- `V_up` 正式数据集；
- `V_down` 正式数据集；
- 每条数据的策略、协议、分支种子和结果记录；
- 父轨迹互不重叠的训练、验证和测试划分。

### 做到什么算完成

- 数据里既有成功，也有失败和边界状态；
- 所有结果数量能够闭合；
- 不把 timeout 当作明确的物理不可行；
- 测试集没有父轨迹泄漏。

## 12. 第八步：训练 `V_up` 和 `V_down`

### 目的

让网络不必对每个新状态都重新跑很多次完整仿真，就能先估计这个状态继续成功的
可能性。

### 为什么保留两个输出

上升和下降问的是两个不同问题。一个状态对“能不能到 Apex”可能很好，但对
“能不能稳定落地”未必好。把所有状态只塞进一个没有阶段含义的分数里，后面很难
解释，也容易学混。

代码可以共享基础结构，但方法上必须保留两个清楚的结果：`V_up` 和 `V_down`。

### 如何完成

1. 只使用策略在实际部署时能观察到的状态特征，不能偷偷使用未来结果。
2. 分别训练上升和下降评分。
3. 处理成功/失败数量不平衡，避免网络永远预测最多的那一类。
4. 在父轨迹隔离的验证集和测试集上检查：

   - 高分状态是否真的比低分状态更容易成功；
   - 预测分数与实际成功比例是否大致一致；
   - 边界状态是否有较高不确定性；
   - 离训练数据很远的状态是否会被错误打成高分。

5. 分数只叫 continuation score。在没有额外证据前，不称为安全概率。

### 产物

- 冻结的 `V_up`；
- 冻结的 `V_down`；
- 数据划分、模型 hash、训练记录和校准报告。

### 做到什么算完成

- 测试集上的排序明显好于随机；
- 高分、中分、低分组的实际成功率有合理区别；
- 没有父轨迹泄漏；
- 模型和它对应的专家策略、数据版本能够一一对应。

## 13. 第九步：建立 soft Tube

### 目的

从整个巨大状态空间里，挑出适合统一策略训练的区域，同时保留一些边界状态，让
最终策略不只会复现一条轨迹。

### 简单理解

soft Tube 不是一条固定轨迹，也不是安全证明。它只是一个带权重的训练状态集合：

- 分数高、数据支持充分的状态多采样；
- 接近成功/失败边界的状态适量采样；
- 明显无效、穿透或离数据太远的状态过滤掉；
- 少量探索状态保留，用来扩展能力。

### 如何完成

1. 用 `V_up` 处理上升状态，用 `V_down` 处理下降状态。
2. Apex 附近同时参考两个分数，形成上下阶段的连接区域。
3. 不预先规定一个固定 top 百分比。先看分数校准、数据密度和实际 continuation
   结果，再决定采样权重。
4. 每个 Tube 记录都绑定模型、数据集、来源策略、XML、配置和筛选规则。
5. 文件中明确写：

   ```text
   training_guidance_only = true
   certified_safe = false
   ```

### 产物

- Tube-up；
- Tube-down；
- Apex overlap；
- 每部分的采样权重和来源记录。

### 做到什么算完成

- Tube 中的每个状态都有来源和评分；
- 训练区、边界区和探索区能分开统计；
- 没有把专家轨迹本身直接叫作 Tube；
- 没有把训练 Tube 说成安全认证。

## 14. 第十步：训练最终统一策略

### 目的

把前面分开学到的能力重新合成一个策略，让最终系统从地面开始，用同一个网络完成
加速、起跳、上升、下降和恢复。

### 如何完成

1. 用 `pi_up_star` 的 Actor 初始化统一策略，因为它已经掌握最难得到的自然起跳。
2. 从 Tube-up、Apex overlap 和 Tube-down 中按比例抽取训练起点。
3. 同时保留一部分自然地面 reset，防止统一策略只会从中间状态开始。
4. 使用完整任务奖励。`V_up/V_down` 只提供有限的采样或辅助引导，不能压过真实
   任务结果。
5. 每个固定 checkpoint 分别检查：

   - 自然起点是否仍然会跳；
   - Apex 状态是否覆盖更多；
   - 下降和落地是否改善；
   - 是否为了落地而破坏起跳；
   - 是否出现只在 RSI 起点成功、自然起点失败的情况。

6. 训练结束后冻结一个 `pi_unified`。实际部署和最终评估都只使用它，不调用
   `pi_up`/`pi_down` 切换器。

### 产物

- 一个冻结的统一策略；
- 完整训练和评估记录；
- 自然起点与各类中间状态的分组结果。

### 做到什么算完成

- 同一个策略能从自然起点完成完整任务；
- 起跳能力没有因为训练恢复而明显退化；
- 落地恢复相比当前 `pi_up` 有明确改善；
- checkpoint、配置、数据和评估来源都可以追溯。

## 15. 最后一步：独立评估

### 目的

确认最终能力来自冻结后的统一策略，而不是训练时挑选状态、专家切换或反复试验
造成的假象。

### 如何完成

1. 冻结 `pi_unified` 后不再改参数。
2. 使用训练中没有用过的随机种子和初始状态范围。
3. 从自然地面起点跑完整任务，不在中途切换专家。
4. 分开报告：完整成功、完成跳跃但恢复失败、起跳失败、物理失败和超时。
5. 另外按初始速度、姿态、小范围扰动等条件画出经验能力范围。

### 做到什么算完成

- 最终报告只使用冻结的统一策略；
- 训练数据、选择数据和最终评估数据互不混用；
- 所有终止原因数量闭合；
- 此时才能讨论经验 JCE/JEL，不能提前声明。
