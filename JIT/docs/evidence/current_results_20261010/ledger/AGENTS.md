## 1. 首要职责

不仅完成当前代码任务，还必须维护研究连续性：知道目标是什么、已经尝试过什么、为什么换路线、目前证据支持什么、下一步解决什么问题。

每次工作遵循“读取状态 → 核实有关事实 → 完成有界任务 → 整理结果 → 更新状态 → 交接”。不要把关键结论只留在聊天回复中，也不要用更多实验或更复杂模块代替明确的研究判断。

## 2. 文档位置、作用域与唯一来源

- `AGENTS.md`：稳定规则、阅读顺序、操作边界和维护协议。规则变化才修改，不逐次追加训练流水账。
- `PROJECT_STATE.md`：目标、当前路线、研究尝试、活动实验、结果、决策、论文证据和下一步。平时主要更新此文件。
- 源码、配置、原始结果仍留在原仓库/运行目录。状态文件保存摘要和可定位证据，不复制大型日志、权重、轨迹。
- 初始化时登记真实 `research_hub`、两个仓库及 JIT 子目录的绝对路径。不得假定路径、分支、checkpoint 或历史文件仍存在。
- 不搬动现有仓库，不重建已有目录结构，不把整个用户主目录初始化为 Git 仓库。
- 两个仓库已有的 `AGENTS.md` 必须保留，增量加入读取本根规则和状态文件的明确路径。检查 `AGENTS.override.md` 与 JIT 子目录规则，不能仅依赖 Git 仓库外的共同父目录自动加载。
- 遵守实际生效的系统、用户和作用域内指令。出现研究路线冲突，记录新旧来源，不静默覆盖；只暂停受冲突影响的操作。
- 无权限读取/写入共享台账时，保存本次待同步摘要或补丁并报告位置，不声称已经同步。不擅自修改全局 Codex 配置、放宽权限或制造第二份权威台账。

## 3. 每次任务开始必须读取

先读取当前作用域有效的代理规则、本文件、`PROJECT_STATE.md` 的总览、对应项目章节、活动实验和最近决策；按需读取引用的实验报告、配置和源码。

随后检查与本任务有关的实际仓库状态：工作目录、分支、HEAD、未提交改动及已登记任务。分清“历史记录中的状态”和“本次实际看到的状态”。检查只读且有界，不扫描无关私人目录，不干扰其他任务。

若用户已提供答案，先利用现有文档和仓库自行解析，不重复询问。非阻断信息写 `UNKNOWN` 并继续能够完成的部分；涉及安全、身份或互相矛盾的关键合同则不得猜测后执行。

## 4. 事实、意图和证据必须分开

用户最新明确决定定义“要做什么”；代码、配置和结果定义“实际上做了什么”。二者不一致时写出实现差距，不能用任一方抹掉另一方。

每条重要记录注明来源类别：

| source_type | 含义 |
|---|---|
| `user_requirement` | 用户明确目标或决定，不代表已经实施 |
| `user_report` | 用户报告的实验表现，原始证据未必已核验 |
| `history_document` | 历史方案、交接或分析文档，只证明文档中的陈述 |
| `repo_artifact` | 已定位到源码、配置、日志、原始指标或 checkpoint |
| `hypothesis` | 解释或设想，尚非事实 |
| `unknown` | 尚无可靠信息 |

另记核验等级 `not_checked / artifact_checked / reproduced`。找到一份旧报告不等于本次已核验其全部底层证据；需要注明“核验了报告文本”还是“核验了原始输出”。`reproduced` 仅用于实际重跑了声明协议的情况，且不是所有历史记录的强制要求。

“代码已写”“训练结束”“评价完成”“候选被采用”“论文结论成立”是不同事件。发现旧结论错误，追加更正、来源和影响，保留原记录，不改写成从未犯过错。

## 5. 历史恢复：先把当下弄清，再逐步补旧账

先登记当前目标、当前路线、当前候选/已采用模型、已知活动实验和下一步，再有界回填历史。优先查现有 `AGENTS.md`、`CURRENT_STATUS.md`、`PROJECT.md`、交接文档、版本历史和被这些文档引用的结果。

只读取获授权且与两个项目有关的历史对话导出或本地任务记录。不能声称能够自动看到其他 ChatGPT 对话或不可访问的历史会话。

按“研究问题/尝试”归档，不按聊天轮次堆砌。一次尝试可以关联多次 run。相同尝试合并索引，原结果不覆盖；未实施提案不登记成已做实验。缺少日期、run_id 或结论依据时保留缺口，不编造。

每轮回填结束写清已覆盖范围和未覆盖范围。不因历史不完整而阻止当前任务，也不以补档为由重跑大量旧实验。

## 6. 每项尝试与每个运行的最小合同

研究尝试至少记录：稳定 ID、问题、假设、方法变化、观察、结论、证据、为何保留/暂停、重新尝试的条件。把“观察到失败”和“推测失败原因”分开。

新实验启动前登记：

```text
experiment_id / project / owner / recorded_at
question / primary_change / hypothesis
code_revision / dirty_patch_or_snapshot
resolved_config / model_and_data_identity / normalizer_identity
initialization: scratch | weights_only | exact_resume
parent_checkpoint / optimizer_and_critic_state / training_step_units
baseline / evaluation_protocol / seeds_or_case_ids / sample_count
budget / resources / stop_rule / acceptance_rule
run_directory / command / host_and_job_identity
execution_status / evaluation_status / adoption_status
```

已有 run manifest 已含这些信息时直接引用，不重复抄配置。历史材料缺项可以写 `UNKNOWN`；新实验的关键配置、来源和预算未明确时，不启动昂贵运行。

状态分别维护：

- 执行：`planned / running / completed / failed / interrupted / blocked / unknown`。
- 评价：`not_started / partial / complete / invalid / unknown`。
- 采用：`not_applicable / pending / adopted / not_adopted / unknown`。

结果至少保存成功数与总数、关键物理指标、基线差异、有效性限制和失败情况。没有结果写 `PENDING`，不写 0。进程消失不等于成功结束；需核对退出信息和预期产物。

## 7. 项目语义与不得混淆的事项

### STTW_CONTROL

长期目标是执行器约束下的稳定控制、驱动—转向协同和可解释的任务偏好。`alpha=0` 路径/转向任务优先，必要时允许减速；`alpha=1` 速度优先，允许一定转向/轨迹偏差，恢复要求以当前协议为准。

当前选择以状态文件中的最新明确决策为准。初始化种子为：上层输出速度/转向参考或参考修正；共同冻结的强底层负责跟踪及底层控制。不得误写为上层直接输出电机动作，也不得把底层残差网络与上层指令网络混为一谈。

区分原始参考、上层调整后的参考、底层实际动作和实测运动。上层是否满足用户请求，应对原始任务评价，不能通过改小参考制造“跟踪成功”。区分 `upper_alpha` 与冻结底层自己的 `lower_alpha`。动作语义、单位、限幅和频率以真实合同为准。

转角跟踪、航向恢复、几何路径恢复并不等价；当前仅测了前两者时，不宣称完整路径跟踪已解决。不同奖励版本的累计 reward 不直接作能力比较。

三头网络和不合理续训等已走过路线必须留档；旧方案失败不代表其所有结构在数学上不可能有效。重新启用须说明新增证据、具体改动及有界验证，而非重复同样尝试。

### DVGC-JIT

长期目标是通过有效扰动探索和策略改进，提高最终跳跃策略的成功率、泛化与经验可达范围。扰动后的真实状态是接续/补训起点；不得擅自改写为“等到临近摔倒才取状态抢救”。快照再训练是否二次施扰，必须遵守对应协议。

分别记录探索策略、基础跳跃策略、生成式/扩散桥接老师、候选学生和已采用学生。老师能恢复、候选轨迹更宽、学生学到了、最终单策略完整任务更强，必须分别提供证据。

扩散/生成模块是正在评价的技术手段，不是必须证明有效的预设结论。记清输入输出、接管窗口、交回对象、训练期/部署期角色和实际优化过的模块。未更新探索器，不得宣称完成了探索器联合迭代。

区分多策略轨迹并集与单个部署策略能力。经验包线不自动等于严格可达集或安全认证。候选未达到采用规则时保留原已采用模型，并同时报告新增、丢失、保留能力；不能只报总成功增加。

## 8. 什么情况下必须更新状态文件

| 触发事件 | 必须更新的内容 |
|---|---|
| 用户改目标、路线或优先级 | 当前路线、决策记录、受影响任务 |
| 网络接口、奖励、观测、物理、基线或评价协议重大变化 | 对应尝试、版本、比较边界及证据关联 |
| 启动、停止、失败或中断重要实验 | 活动实验、运行身份、预算和状态 |
| 新日志/完整结果返回 | 结果摘要、有效性、结论、采用状态、论文证据 |
| 找到旧失败或发现旧解释错误 | 历史尝试、更正、避免重复的条件 |
| 任务结束或交接 | 当前状态、未完成事项、下一步、所需入口 |

观察到变化就在当前任务内更新，不等用户提醒。纯拼写修正不制造研究里程碑；能够影响模型表现、复现或论文结论的变化属于重大更新。

结果已产生但 Codex 未运行时，本文件本身不会监控任务。下次会话优先导入已登记运行的新结果；若已有获授权的结果收集流程，可复用其完成产物。新增自动收集仅作为独立工程任务，不能声称一份 Markdown 已实现后台维护。

## 9. 并行工作与资源保护

每个项目维护自己的尝试、活动实验和下一步；不得因处理另一项目而删除其未完事项、改分支、停止任务或占满其资源。

共享状态文件由单一写入者串行合并。多会话需要写入时，使用共同约定的文件锁；必须在锁内重新读取最新版、增量修改再写回。仅比较旧哈希或原子替换并不能代替并发协调。不能协调时输出待合并补丁，不覆盖整份文件。

任务登记包含负责人、分支/worktree、输出目录及资源占用。根文档汇总不授权启动额外训练；新训练必须符合当前用户任务和已登记预算。不无上限续训，不借管理任务做大规模调参。

## 10. 代码、实验和提交纪律

修改前检查现有实现与未提交工作；优先最小补丁。不得覆盖用户改动、重置其他 worktree、删除旧结果，或擅自终止不属于本任务的进程。

不静默改变 XML、摩擦、步长、奖励、观测或动作含义来获得更好结果。真实变化须记录新协议和不可直接比较的旧结果。训练/开发/最终测试的来源与复用情况须声明，不能根据最终测试反复调参后仍称未见泛化。

验证以必要接口检查、针对性测试和回答核心假设的实验为主。测试通过不等于控制效果成功；reward 平滑不等于论文问题解决。

代码或实验变化应和对应状态更新一起交付。提交遵守当前授权；不自动 push，不为文档维护创建未经请求的常驻服务、全局工具或依赖升级。

## 11. 每次交付的完成标准

结束前确认：新增决定已写入；实际修改和结果已登记；失败/不确定性未隐去；已采用模型与候选模型未混淆；活动实验状态有检查时间；论文表述与证据等级一致；下一步不超过三个明确行动，并说明它们解决的问题。

最终回复概括：本次做了什么、结果支持/不支持什么、更新了哪些记录、仍在运行/阻塞什么、下一步。未执行或未核验事项直说；状态未写入时不得声称交接完成。

## 12. 文档维护与归档

状态总览始终保持简短，每个项目只保留一个清晰的当前主线。历史记录保留时间顺序与稳定 ID；被取代的路线标明 successor，不删除。

当文件妨碍阅读时，将已关闭尝试的详细内容迁入一个归档文件；根台账仍保留摘要、结论、重试条件和精确链接。不要每次会话另造一份 CURRENT_STATUS、FINAL_REPORT 或“最终版”。

规范格式为 UTF-8 Markdown。未知值显式填写，日期使用绝对日期，运行时间尽量保留时区。文档规则本身的变更要说明原因，不得借更新规则偷偷降低实验门槛。
